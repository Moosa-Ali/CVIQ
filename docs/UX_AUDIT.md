## 1. Executive summary

The backend is architecturally solid: a clean canonical-JSON model, a deterministic AI-free render pipeline, dual-mode (JD / no-JD) analysis, gap engine, confidence flags, vision fallback for scanned PDFs, and passing smoke tests. **The weakness is almost entirely in the product layer** — the SPA that users actually touch:

1. **The Optimize flow is a one-way conveyor belt, not an optimization loop.** Upload → Analyze → Suggestions → Chat ends in a dead end. There is no "re-analyze to see my new score", no before/after comparison, and the exported result is never tied back to the analysis.
2. **Free chat is a hidden, stateless text box.** It is the 4th wizard step, sends no conversation history to the LLM, and its output **cannot be applied to the CV** — the user must copy-paste AI text into the editor by hand.
3. **The editor is a plain form, not an editor.** No reordering of items/bullets/sections (not even up/down arrows), no custom sections (despite being in the schema and the SRS), no undo, no autosave, and a **placebo "Apply changes" button** that does nothing.
4. **The live preview is not WYSIWYG.** It is a hand-written HTML approximation of one generic layout; it never renders the actual selected design, and the 20 gallery templates have no preview at all once you are editing.
5. **Several features are broken promises vs. the SRS/design docs:** `reorder`/`layout`/`rename` suggestions are generated by the AI but **silently do nothing when applied**; `custom_sections` are parsed and exported but invisible/uneditable; the analysis report's own `suggestions` and the parsed `JDProfile` are fetched and never displayed.
6. **Everything is lost on refresh.** No draft persistence, no autosave (the design doc explicitly promises "persistent autosave"), and the parse session dies after 30 minutes with inconsistent error behavior.
7. **Look & feel is "demo-grade":** emoji as icons, a placebo button, destructive actions without confirmation, landing on the Settings page, and two parallel template systems that behave differently depending on which door you entered through.

Section 16 contains a prioritized (P0–P3) remediation plan; Section 17 describes the corrected target workflows.

## 3. Critical findings (P0)

### 3.1 Structural suggestions (`reorder` / `layout` / `rename`) are generated but never applied
> **Status (2026-08-11): Fixed** — `reorder` suggestions are applied (item-level via `move_from`/`move_to`; section-level via `target_section` + `up/down/top/bottom/N`) and `rename` updates `section_titles`/custom-section titles; `layout` was removed from the prompts and is a parseable no-op on apply; renderers honor `section_order`/`section_titles`. (§1.1 P0-1; S19, S27.)
- **Evidence:** The LLM is explicitly prompted to emit `reorder`/`layout`/`rename` suggestions with `move_from`/`move_to`/`target_section` (`app/services/cv/tailor.py:79-98,163-184`; `analyzer.py:152-228`). The model parses them (`models.py:121-123`). **Nothing consumes them:** `tailor.apply_suggestion()` (`tailor.py:531-671`) has branches for summary/experience/education/skills/projects/certifications/languages/custom/personal — no branch for reorder/layout/rename, so the CV is returned unchanged. `move_from`/`move_to` are never read anywhere outside the model definition.
- **UI makes it worse:** the suggestions list shows *"Structural suggestion — applies to the regenerated export layout"* (`app.js:1584`) — this statement is **false**. Exports render the canonical JSON through fixed templates; no layout is ever regenerated from these suggestions.
- **User impact:** user accepts a "Move Skills above Experience" suggestion, clicks *Apply accepted*, gets `0 suggestions changed the CV` (or worse, a success toast when other suggestions applied) and the promised change never happens. This directly violates SRS FR-5.1/FR-5.6.
- **Fix:** either (a) implement reorder/rename application — reorder array items / rename section headings in the canonical JSON and honor section order in `render_html` — or (b) stop generating these types (remove from prompts) until implemented. Add a smoke test: accept a `reorder` suggestion → `applied >= 1` and item order changes.

### 3.2 "Apply changes" button in the Editor is a placebo
> **Status (2026-08-11): Fixed** — the placebo button is removed; the Editor toolbar is now ATS Check, Re-analyze (score delta), Assistant, and Save to library (Ctrl+S). (§1.1 P0-2.)
- **Evidence:** `app.js:2016-2020` — the handler only re-renders the preview and shows the toast *"Changes applied to your CV — ready to export"*. But every input already mutates `CURRENT_CV` live and re-renders on every keystroke (`app.js:1862-1912`). The button commits nothing, saves nothing, validates nothing.
- **User impact:** erodes trust; users reasonably believe edits are NOT saved until they click it, and may think export uses un-applied data if they don't.
- **Fix:** remove the button entirely, or repurpose it honestly (e.g. "Save draft" that persists to the library/localStorage). Replace the preview-toolbar slot with something real: ATS **Check** (already exists) and a **Re-analyze** action.

### 3.3 Accepted-then-applied suggestions can be re-accepted and double-applied
> **Status (2026-08-11): Fixed** — applied cards are locked ("Applied ✓", all actions disabled), `applyAccepted` filters already-applied ids, and append-style suggestions dedupe identical items server-side; re-applying the same set yields `applied == 0`. (§1.1 P0-3; S20.)
- **Evidence:** after `applyAccepted()`, applied suggestions get `_state='applied'` (`app.js:1647`). In `renderSuggestionList` the *Accept* button is only disabled for `'accepted'` (`app.js:1587`) — an `'applied'` card can be *Accept*-ed again and re-applied. For `add`-type suggestions (skills, keywords, bullets) `tailor.apply_suggestion` **appends** (`tailor.py:595-601, 653-657`), producing duplicates.
- **Fix:** disable all actions on `applied` cards (show an "Applied ✓" state), and/or make `applyAccepted` filter out already-applied ids. Re-applying the same suggestion set should be idempotent.

### 3.4 Everything is lost on refresh — no draft persistence, no autosave
> **Status (2026-08-11): Fixed** — debounced autosave to `localStorage['cviq.draft.v1']` (cv + optimize state + chat + build state), "Resume where you left off?" prompt, `beforeunload` guard, and an "Unsaved changes" indicator. (§1.1 P0-4; design §7.2.)
- **Evidence:** all state lives in module globals (`CURRENT_CV`, `OPT_STATE`, `CHAT_LOG`, `BUILD_STATE` — `app.js:7-13`). No `localStorage`/`sessionStorage` anywhere. `design.md:630` explicitly specifies *"Local 'Save to library' + persistent autosave (canonical JSON)"* — autosave was never implemented. There is also no `beforeunload` guard.
- **User impact:** an accidental refresh, navigation, or browser crash after 30 minutes of tailoring wipes the CV, the analysis, the suggestions review state, and the chat. For a CV tool this is a product-killer.
- **Fix:** debounce-persist `CURRENT_CV` (and the optimize session: JD, report, suggestions, chat) to `localStorage`; restore on load with a "Resume where you left off?" prompt; add a `beforeunload` warning when there is unsaved work. This is a few dozen lines — no backend change needed.

### 3.5 `custom_sections` are parsed and exported but invisible and uneditable
> **Status (2026-08-11): Fixed** — custom sections are editable in Build and Editor (title + bullets, add/remove/reorder/duplicate), included in `emptyCV()`, and rendered in the preview and exports. (§1.1 P1-12.)
- **Evidence:** the schema has `custom_sections` (`models.py:61-84`), the parser extracts them (`parser.py:619`), exports render them (`render_html.py:210`, `docx_export.py:136`), `apply_suggestion` patches them (`tailor.py:649-664`) — but the frontend has **zero** support: `emptyCV()` omits the field (`app.js:15-28`), neither the Build form nor the Editor renders them, and `renderPreview` never shows them.
- **User impact:** a user uploads a CV with an "Awards" or "Publications" section → it survives silently in the JSON, appears in the PDF, but can never be seen, edited, reordered, or deleted in the UI. Directly violates SRS FR-2.1 and FR-6.1 ("editor for all canonical sections incl. custom_sections").
- **Fix:** add a "Custom sections" card to both Build and Editor (title + bullets, add/remove), render them in the preview, and include them in `emptyCV()`.

### 3.6 Destructive actions with no confirmation and no undo
> **Status (2026-08-11): Fixed** — Reset requires a confirmation modal; remove flows are confirmed in-context; all AI text actions (bullets/project/skills) preview the generated text first with **Replace / Append / Cancel** (nothing overwrites silently) and the form re-renders after applying. (§1.1 P0-5.)
- **Evidence:** the **Reset** button instantly replaces `CURRENT_CV` with an empty CV — no modal, no undo (`app.js:450, 740`). *Remove* on any repeater item splices immediately (`app.js:773-781, 1951-1957`). *AI Assist Bullets* **replaces all bullets** of a chosen experience item with generated text, with no preview of the generated text before overwriting (`app.js:680-696`).
- **Fix:** confirmation modal for Reset/Remove (or better: a lightweight undo toast — "Item removed · Undo"); for AI-generated content always show the draft first with *Replace / Append / Cancel* options.

### 3.7 Parse session expiry behaves inconsistently — chat hard-fails, other paths silently degrade
> **Status (2026-08-11): Fixed** — unified `_resolve_session` in `routes/cv.py`: analyze/suggest/chat/gaps all degrade gracefully on a missing/expired session (never 404, never silence) and return a structured `session_warning` the UI surfaces. (§1.1 P0-6; design §2.4; S21.)
- **Evidence:** session TTL is 30 min (`session.py:18`). On expiry, `/api/cv/analyze`, `/tailor/suggest`, `/gaps` silently degrade to the self-contained request body (`routes/cv.py:184-189, 227-232, 316-319`), but `/api/cv/tailor/chat` raises **404 "session expired or not found"** (`routes/cv.py:271-273`). For scanned PDFs, silent degradation means the vision path is silently lost and analysis quality drops without any notice.
- **Fix:** make chat degrade like the others (it has `cv` in the body), and when a session id was supplied but is gone, return a structured warning the UI can surface ("Upload session expired — re-upload for best results on scanned PDFs") instead of either a raw 404 or silence.

## 4. Core workflow gaps (P1)

### 4.1 The Optimize flow is linear and dead-ends — there is no improvement loop
> **Status (2026-08-11): Fixed** — the wizard is now the 5-step loop Upload → Analyze → Review → Apply → **Results & Export** with score delta vs base, sparkline (`scoreHistory`), applied-changes summary, PDF/DOCX, Re-analyze and Keep editing; stale suggestions are flagged after edits. (§1.1 P1-8; design §7.3.)
Current: `Upload → Analyze → Suggestions → (Apply → dumped into Editor) → Chat`.
- **No closed loop:** after applying suggestions the app jumps to the Editor (`app.js:1656`) and never offers **"Re-analyze"** to show the new ATS score. The single most satisfying moment of an optimizer — *"your score went 62 → 84"* — does not exist.
- **No before/after:** no diff view of the CV before vs. after applying; no record of what changed.
- **Export is not part of the wizard.** The flow never ends with "Download your tailored CV"; the user must know to go to the Editor. (Matches your own description: *optimize → suggestions → apply → download → free chat* feels stitched together.)
- **Suggestions go stale:** after generating suggestions, any edit in the Editor (or re-parse) invalidates them, but nothing marks them stale.
- **Fix (target flow):** `Upload → Analyze (score) → Review gaps+suggestions → Apply → Re-analyze (new score, delta) → Export → optional Chat`. Keep the wizard pills, but add a final **"Results & Export"** step showing score delta, applied-changes summary, and PDF/DOCX buttons. See §17.1.

### 4.2 Free chat is hidden, stateless, and cannot edit the CV
> **Status (2026-08-11): Fixed** — Chat 2.0: full history sent (last ~20), response contract `{reply, proposed_edits, session_warning}`, proposed edits rendered as diff cards and applied via `/api/cv/tailor/apply`; dockable Assistant in the Editor and on every Optimize step; quick-target chips; copy button; markdown-ish rendering; Enter/Shift+Enter hinted; chat persists in the draft. (§1.1 P1-9; design §7.4; S21.)
- **Hidden:** it is wizard step 4/4, reachable only via the pill or the *Next: Tailor Chat* button; it is absent from the Editor (where it would be most useful) and from the nav.
- **Stateless:** each message calls `tailor.rewrite_segment(cv, "", jd, segment=text, context="", client)` (`routes/cv.py:279`, `tailor.py:685-705`). **No conversation history is ever sent** — the backend treats the whole user message as a "segment to rewrite". Follow-ups like "make it shorter" cannot work. The `context` field is dead (frontend always sends `''` — `app.js:1705`).
- **Cannot edit the CV:** the AI reply is rendered as a chat bubble (`app.js:1690`). There is no "Insert into Summary / Experience 1 / Skills" action, no field targeting, no diff — the user must manually copy text out of the bubble and paste it into a form field. This is exactly your complaint, and it is the feature's biggest gap.
- **UX nits:** send requires the button or **Ctrl+Enter**, which is never hinted; plain Enter inserts a newline. No markdown rendering, no copy button, no persistence (`CHAT_LOG` wiped on reset, `app.js:1008`).
- **Fix:** see §17.2 — make chat a first-class, field-aware assistant: send full history, let the model return `{reply, proposed_edits:[Suggestion]}`, render proposed edits as inline diff cards with **Apply** buttons that patch `CURRENT_CV` through the existing `/api/cv/tailor/apply` machinery. Surface the chat as a dockable panel in the Editor, not a buried wizard step.

### 4.3 The Editor cannot reorder anything
> **Status (2026-08-11): Fixed** — ↑/↓ move buttons on every repeater item and bullet row, plus duplicate-item; section order is user-controlled via applied `reorder` suggestions and honored by every renderer through `CVData.section_order`. (§1.1 P1-10; S19, S27.)
- **Evidence:** repeater items (experience, education, projects, certifications, languages, skill groups) and bullets have only *Remove* and *Add* (`app.js:1780-1823`). No drag handles, no ↑/↓ buttons, no section reordering, no drag-and-drop anywhere. Section order is hard-coded in `editorFormHTML()` and in every export template.
- **User impact:** reordering entries (e.g. most relevant job first after tailoring) is one of the most common CV edits; today it requires delete-and-retype. Your complaint is confirmed in code.
- **Fix:** add ↑/↓ move buttons on every repeater item and bullet row (cheap, accessible), plus drag handles with HTML5 drag-and-drop as an enhancement. Later: user-controlled **section order** stored in the canonical JSON and honored by `render_html` (this also gives `reorder` suggestions somewhere real to land — see 3.1).

### 4.4 Preview is not WYSIWYG — two different "templates" exist
> **Status (2026-08-11): Fixed** — `POST /api/export/preview` server-renders the real Jinja2 HTML for the current `CVData` + template id (builtin or gallery, `Cache-Control: no-store`) into a debounced A4-framed iframe with zoom / fit-width controls; the hand-written `renderPreview` approximation is retired. (§1.1 P1-11; S22.)
- **Evidence:** `renderPreview()` (`app.js:2133-2223`) is a hand-written HTML sketch of a single generic layout. It never uses the Jinja2 templates that produce the actual PDF (`app/templates_html/*.html.j2`), so fonts, spacing, two-column designs, headings — all differ from the download. Gallery templates (the 20 PDF designs) have **no editing preview at all**: the Build form doesn't even contain a `#preview-root` element, yet calls `renderPreview(document.getElementById('preview-root'))` — a no-op (`app.js:766, 976-978`). The Editor's template picker only lists the 3 generic templates (`/api/meta`), so a gallery design chosen in Build cannot be previewed or changed in the Editor.
- **User impact:** "what you see is NOT what you download". Users pick a beautiful gallery design, then edit blind.
- **Fix:** server-rendered preview: `POST /api/preview` (or reuse the render pipeline) returning the real Jinja2 HTML for the current `CVData` + template id, shown in an iframe/`srcdoc`, debounced on input. Retire the hand-written `renderPreview` approximation. Unify the two template systems (§5.2).

### 4.5 Two parallel template systems with two pickers and two export paths
> **Status (2026-08-11): Fixed** — one unified catalog (`GET /api/templates`: 3 builtin `source:"builtin"` + 20 gallery `source:"gallery"`), one picker with friendly "Dedicated design"/"Closest match" labels, one export/path resolution (`/api/export/pdf|docx`, `/api/export/preview` and `/api/templates/{id}/export/*` all accept any catalog id); DOCX now uses the CV accent. (§1.1 P1-11; S17, S23.)
- **System A:** 3 generic templates (`modern/classic/minimal`, `app/templates.py`) — picked via segmented control, exported via `/api/export/pdf|docx`.
- **System B:** 8 gallery designs (`Templates/*.pdf` — dummy-data PDFs rendered from the 8 Jinja2 templates; the original 20 designs live in `Templates/Archive/`) — picked via gallery cards, exported via `/api/templates/{id}/export/pdf|docx`.
- **Consequences:** the Editor can't see/change a gallery choice; Build can't preview generic choices next to gallery ones; "converted / fallback" badges leak internal jargon to users; and the DOCX variant of a gallery export silently ignores the design entirely (§8.1).
- **Fix:** one catalog, one picker: `GET /api/templates` should return every design (generic + gallery) with `render_template`, thumbnail, and a "converted/closest-match" user-friendly label; the Editor template picker should consume the same catalog; export should be a single endpoint taking a template id.

### 4.6 No re-analysis / progress tracking
> **Status (2026-08-11): Fixed** — ATS scores accumulate in `OPT_STATE.scoreHistory` (persisted in the draft); Re-analyze buttons in the Review step, the Results & Export step and the Editor show the new score with the delta vs `baseScore`, and a sparkline renders the history. (§1.1 P1-8.)
- The ATS score is computed once. After the user applies suggestions or edits, there is no way to see improvement without starting a whole new wizard pass (and even then, no delta is shown). Score history is not kept.
- **Fix:** keep `ats_score` history in `OPT_STATE` (and localStorage); show "62 → 84 (+22)" after re-analyze; optionally a tiny sparkline in the results step.

### 4.7 Analysis report data is fetched and thrown away
> **Status (2026-08-11): Fixed** — the report's `suggestions` are importable into Review with one click ("Import N analysis suggestions"); `jd_profile` renders as a "We understood the job as …" summary card; the gaps panel is unified (deterministic + semantic GapDiffs + report gap strings with kind/severity, de-duplicated, each convertible to a suggestion). (§1.1 P1-14.)
- `AnalysisReport.suggestions` (`models.py:177`) is returned by `/api/cv/analyze` but `renderReport()` never renders it — the user must separately click *Generate Suggestions* (a second LLM call) in step 3. Either merge them (offer "Import N suggestions from analysis") or stop generating them in analyze to save tokens/latency.
- `/api/cv/gaps` returns `jd_profile` (SRS FR-9.3) — role title, required/nice-to-have skills, keywords — but `renderGaps()` never displays it. Showing the parsed JD profile ("We understood the job as: Senior Backend Engineer — must-haves: Python, AWS…") is high-value reassurance that the JD was understood.

## 13. Proposed target workflows

> **Status (2026-08-11):** this section now describes the SHIPPED flows. One delta vs §13.1: suggestions are still generated by their own step (a second LLM call), but the analysis report's suggestions import into Review in one click ("Import N analysis suggestions") — the single round-trip was not adopted. Chat (§13.2) and Editor (§13.3) match the implementation, except Editor undo/redo, drag-and-drop reorder, and per-item AI menus remain future work (Assistant panel covers the per-item case).

### 13.1 Optimize (loop, not line)
```
Upload / Pick CV ──▶ Analyze (JD optional) ──▶ Review ──▶ Apply ──▶ Results & Export
     │                   │                      │           │            │
     │                   ├─ ATS score           │           │            ├─ new score + delta (62 → 84)
     │                   ├─ JD profile card     │           │            ├─ applied-changes summary
     │                   ├─ gaps (one panel)    │           │            ├─ PDF / DOCX buttons
     │                   └─ suggestions (auto)  │           │            ├─ "Re-analyze" / "Keep editing"
     │                                          │           │            └─ "Open chat" (optional)
     └─ confidence flags checklist (confirm inline, not a separate dead-end)
```
- Suggestions generate **with** the analysis (single LLM round-trip or parallel), not as a separate click.
- Chat is available from **every** step as a side panel — not a terminal wizard step.

### 13.2 Chat (assistant, not text box)
- Sends full conversation history + current `CVData` + JD.
- Response contract: `{reply: string, proposed_edits: Suggestion[]}`.
- Proposed edits render as mini diff cards (field, before → after, rationale) with **Apply / Dismiss**; Apply calls the existing `/api/cv/tailor/apply` and updates the Editor + preview immediately.
- Quick-target chips: "Summary", "Experience 1 bullets", "Skills" — so the model knows the field_path to patch.
- Persisted per CV in localStorage; copy button + markdown rendering.

### 13.3 Editor (a real editor)
- Reorder: ↑/↓ on every item/bullet (drag handles as enhancement); section order editable and honored by export.
- Custom sections: add/remove/edit, rendered in preview and export.
- Live preview = server-rendered real template (iframe), with page-boundary lines and zoom.
- Per-item AI menu (rewrite / quantify / shorten / match JD) with preview modal.
- Autosave draft (localStorage) + explicit Save-to-library with overwrite; unsaved-changes indicator.
- Inline ATS Check badges on offending fields; suggestion-status markers (FR-6.3).
- Undo/redo for structural ops; duplicate item; "Present" date toggles; skills chip editor.
